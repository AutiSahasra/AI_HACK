# System Limitations & Operational Boundaries (`docs/LIMITATIONS.md`)

This document outlines the current boundaries, deliberate trade-offs, and design limits of the **AI Root Cause Analysis & Intelligent Ticket Resolution Copilot**.

---

## 1. Decision-Support Boundary (Human-in-the-Loop)
- **Decision-Support by Design**: The copilot does not autonomously replace human engineering judgment. All root cause explanations generated by AI are classified as `"Hypothesis – unverified"` until an engineer or approver marks them verified.
- **Explainability Requirement**: The UI strictly separates `Observed Facts` (derived directly from logs) from `AI Inferences` (probabilistic deductions). Engineers must verify inferences against system telemetry before authorizing high-risk changes.

---

## 2. Remediation Safety Boundaries
- **Strict Allow-Listing**: The system permits execution of **only** explicitly compiled, allow-listed remediation actions:
  - `restart_demo_service`
  - `clear_demo_cache`
  - `rollback_demo_config`
- **Zero Arbitrary Execution**: There is **no shell execution, no arbitrary bash scripts, and no dynamic command injection**. Any attempt to supply custom shell commands is rejected by the backend policy layer.
- **Backend-Enforced Authorization**: Dual-authorization is strictly verified at the backend API boundary; client-side bypass attempts (direct POST to `/api/remediation/execute`) are rejected with HTTP 403.
- **Self-Approval Prohibition**: Requesters cannot approve their own remediation requests.

---

## 3. Telemetry & Log Volume Boundaries
- **In-Memory Windowing & Context Truncation**:
  - The RCA service samples the top 50 representative error/warning events (up to 4,000 characters) to construct the prompt evidence corpus.
  - In massive log bursts (>100,000 logs/min), events outside the active incident's correlation window or beyond the sampling cap are persisted in MongoDB but omitted from the immediate LLM prompt.
- **Single-Node Async Workers**:
  - Background tasks (RCA generation, recovery verification loops) execute as native Python `asyncio` tasks without external task queues (e.g. Celery/Redis).
  - While this eliminates operational overhead and infrastructure dependencies for demo and staging environments, enterprise multi-node deployments with heavy concurrency should front the worker layer with Redis/Celery or Kafka.

---

## 4. Search & Retrieval
- **Lexical Text Indexing**:
  - Historical incident and runbook retrieval uses MongoDB compound text indexes (`$text` search) with service filtering.
  - While fast and zero-cost, it relies on lexical keyword overlaps rather than dense semantic embeddings. A vector database layer (e.g. MongoDB Atlas Vector Search or Qdrant) can be plugged in via the `Retriever` interface when dense embedding models are configured.

---

## 5. Live Ingestion
- **Collector Footprint**:
  - The included Python log collector tails local log files with byte-offset tracking and batches requests to `/api/ingest`.
  - For large-scale distributed Kubernetes clusters, enterprise log forwarders (FluentBit, Vector, Promtail) should be configured to stream directly to `/api/ingest` using the provisioned API keys.
